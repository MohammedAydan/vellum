# الصفحة الرئيسية للتوثيق

VELLUM هي قاعدة بيانات مستندات متعددة المستأجرين مبنية بالكامل على PostgreSQL/JSONB. تحصل على مجموعات هرمية، ومستندات JSON مكتوبة، واستعلامات منظمة مع ترقيم صفحي عبر المؤشرات، وتحويلات حقول ذرية، ومعاملات تحكم متفائل في التزامن، وتدفقات WebSocket المباشرة — كل ذلك عبر SDK صغير بلغة TypeScript/JavaScript (`@vellum/sdk-js`) أو عبر HTTP مباشر.

يوجد **اعتماد حالة واحد فقط وقت التشغيل: PostgreSQL**. لا يوجد Redis، ولا وسيط رسائل، ولا خدمة تخزين مؤقت منفصلة. يُبنى الوقت الفعلي على `LISTEN/NOTIFY` الخاص بـ PostgreSQL إضافةً إلى صندوق بريد دائم (outbox)؛ ويستخدم التخزين المؤقت وتحديد المعدل حالات قصيرة العمر داخل العملية مع دعم من PostgreSQL حيث يلزم الديمومة؛ أما المعاملات فهي معاملات PostgreSQL أصلية.

:::note
واجهة المستندات العامة في VELLUM محددة بمفتاح API مع رمز مستخدم نهائي اختياري بخوارزمية EdDSA. أما لوحات التحكم فتستخدم رموز جلسة Console/Admin خاصة بكل مجال (`/v1/console/...`، `/v1/admin/...`). المجالات الثلاثة المعزولة تشترك في عناصر التشفير فقط — راجع [مصادقة المستخدمين والمجالات الثلاثة](./end-user-auth.md).
:::

## السيناريو

تخيل أنك تبني تطبيق إدارة مهام متعدد المستأجرين. يحصل كل عميل (مستأجر) على مشروعه الخاص، وتحتاج إلى تخزين المهام، والاستعلام عن المهام المفتوحة، والتفاعل مع التغييرات لحظيًا، والاحتفاظ بسجل تدقيق صارم — كل ذلك دون تشغيل خدمة تخزين مؤقت أو وسيط رسائل منفصل. يمنحك VELLUM واجهة مستندات واحدة مدعومة بـ PostgreSQL تعالج هذه الجوانب وتحدد نطاق كل طلب إلى زوج `(projectId)`.

```ts
// عميل واحد، نطاق مستأجر واحد: كل طلب يحمل projectId.
import { createClient } from "@vellum/sdk-js";

const db = createClient({
  projectId: "<YOUR_PROJECT_ID>",
  apiKey: "<YOUR_API_KEY>", // pk_ للمتصفح/الجوال، sk_ على خادم موثوق
});

// قراءات وكتابات مستوى البيانات محددة دائمًا بـ (project).
await db.collection("tasks").doc("task_123").set({ title: "Ship v1", done: false });
const snap = await db.collection("tasks").doc("task_123").get();
console.log(snap.data());
```

## البنية في 60 ثانية

تقسم المنصة تخزينها إلى قاعدتي بيانات منفصلتين فيزيائيًا ومنطقيًا:

| المستوى | قاعدة البيانات | ما الذي يوجد هناك |
| :--- | :--- | :--- |
| **مستوى التحكم** | `control_db` | المستخدمون، والمؤسسات، والعضويات، والمشاريع، ومفاتيح API بادئاتها `pk_`/`sk_` وتجزئاتها (hashes)، ومجموعات قواعد الأمان المرجّلة، وأسرار MFA، وعدادات الاستخدام اليومية، وسجلات التدقيق غير القابلة للتعديل. |
| **مستوى البيانات** | `data_db` | مستندات العملاء، وتعريفات الفهارس المركّبة وإدخالاتها، و`realtime_outbox` للمعاملات، وجدول `transactions` الخاص بـ OCC. |

ينتج عن هذا التقسيم ثلاث ثوابت:

1. **التهيئة الأولية لا تعتمد أبدًا على بيانات العملاء.** تشغيل الخدمة، ومصادقة المشغّلين، والتحقق من مفاتيح API، والتعافي من الانقطاع تقرأ فقط من `control_db`. لا يوجد اعتماد دائري على واجهة المستندات العامة.
2. **كل عملية في مستوى البيانات محددة بالمستأجر.** يحمل كل طلب `(projectId)`، وتربط كل معاملة `SET LOCAL app.current_project_id` و`statement_timeout = '5000ms'`. تفشل سياسات PostgreSQL Row-Level Security تلقائيًا (fail closed) إذا غاب هذا السياق. المشروع هو المستأجر الوحيد.
3. **فهارس المستأجر لا تأخذ أقفال DDL أبدًا.** الفهارس المركّبة هي صفوف في `document_indexes` بمفاتيح فرز ثنائية تحافظ على الترتيب في `document_index_entries` — ولا يُنفَّذ `CREATE INDEX` على جدول `documents` المشترك مطلقًا.

### مبدأ «صفر Redis»

سمّى التصميم الأصلي 2.0 خدمة Redis كوسيط إلزامي للوقت الفعلي. تم **إلغاء** هذا الشرط. في التصميم الحالي:

- كل تعديل يكتب صفًا في `realtime_outbox` **في نفس معاملة قاعدة البيانات** التي تعدّل المستند.
- يُصدر مُحفّز `AFTER INSERT` إشعار `NOTIFY` صغيرًا يحتوي فقط على رقم التسلسل ومعرّفات المستأجر — ولا يحتوي أبدًا على بيانات المستند.
- عميل PostgreSQL واحد مخصص لـ `LISTEN` يستقبل الإشعار ويوقظ مستطلع صندوق البريد الذي يكتشف الفجوات، والذي يجلب الصفوف الكاملة عبر المهايئ المحدد للمستأجر ثم يوزّعها عبر WebSockets.
- مخابئ المفاتيح المتحقق منها، وإلغاء الجلسات، ونوافذ تحديد المعدل هي هياكل TTL داخل العملية؛ ويتم الإبطال عبر الحالات باستخدام `NOTIFY vellum_cache_invalidate`.

راجع [الوقت الفعلي](./realtime.md) و[قائمة التحقق للإنتاج](./production-checklist.md) للتفاصيل التشغيلية.

## حول الأمثلة

قد تتضمن كل دالة كتلة مثال، تُكتب كتوجيه example-tabs متبوع بمعرّف مسجّل. يوسّع مولّد الموقع الثابت كلًا منها إلى **كتلة مصدر ثابتة مرفقة بمخرجات تشغيل حقيقية**. يتم التحقق من الأمثلة بتشغيلها فعليًا مقابل قاعدة الكود؛ ولا تُظهر الوثائق سوى المصدر والمخرجات المسجّلة.

:::warning
الوثائق **لا تنفّذ أي كود في المتصفح**. كتل الأمثلة عناصر ساكنة معروضة مسبقًا. لا تُلصق أبدًا مفاتيح API حقيقية أو رموز جلسة أو عناوين URL لقواعد بيانات في الوثائق أو في التحكم بالمصادر — جميع المقتطفات هنا تستخدم عناصر نائبة مثل `<YOUR_API_KEY>`.
:::

## الأخطاء الشائعة

- **لا تضف وسيط رسائل أو خدمة تخزين مؤقت.** PostgreSQL هو الاعتماد الوحيد وقت التشغيل؛ يُبنى الوقت الفعلي والتخزين المؤقت قصير العمر عليه.
- **المفتاح العام ليس منحة وصول.** كل عملية على المستندات تظل تمر عبر قواعد أمان البيئة.
- **لا تنفّذ `CREATE INDEX` على `documents`.** تُدار الفهارس المركّبة كصفوف عبر واجهة الفهارس، لذا لا تأخذ فهارس المستأجرين قفلًا على الجدول المشترك.
