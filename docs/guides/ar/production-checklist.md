# قائمة التحقق للإنتاج

استخدم هذه القائمة قبل استقبال حركة المرور. لدى VELLUM قاعدتا PostgreSQL ولا توجد أي خدمة أخرى تحمل الحالة.

## السيناريو

أنت تروّج نشرًا من بيئة staging إلى الإنتاج. قبل توجيه حركة المرور تُبدّل إلى `DATABASE_MODE=postgres`، وتستبدل كل سر تطوير، وتُوجّه فحوص الصحة إلى `/v1/health/ready`، وتتأكد من عمل عمال الخلفية الثلاثة، وتُجرّب استعادة قاعدتي البيانات.

```bash
# بوابة تحقق بسيطة قبل التشغيل: تفشل إذا لم تكن الجاهزية خضراء.
curl -fsS http://localhost:8080/v1/health/ready | jq -e '.ready == true' >/dev/null \
  && echo "ready to serve traffic" || { echo "not ready"; exit 1; }
```

## وقت التشغيل والطوبولوجيا

- **Node 22 أو أحدث.** المستودع يستهدف `>=22`؛ وصورة الإنتاج `docker/Dockerfile.api` هي حاوية `node:22-alpine` متعددة المراحل تعمل بغير مستخدم جذري (`uid 1001`) على المنفذ `8080`.
- **قاعدتا بيانات.** `control_db` (5432 محليًا) و`data_db` (5433 محليًا). لا تضف حاوية Redis/وسيط/تخزين مؤقت — التصميم لا يحتوي عليها صراحةً.
- **اضبط `DATABASE_MODE=postgres`.** الوضع الافتراضي `memory` مخصص للاختبارات المعزولة فقط.
- **Neon / serverless:** قراءات الاستعلام الواحد يمكنها استخدام مشغّل HTTP؛ أما المعاملات فتستخدم `Pool` عبر WebSocket/TCP. ويستخدم DDL والترحيلات اتصالات `*_DATABASE_URL_DIRECT` المخصصة.

## الأسرار والتهيئة

استبدل كل قيمة تطوير افتراضية وتحقق منها عند التشغيل:

```bash
NODE_ENV=production
DATABASE_MODE=postgres
CONTROL_DATABASE_URL="postgres://.../control_db"
DATA_DATABASE_URL="postgres://.../data_db"
DATA_DATABASE_URL_LISTEN="postgres://.../data_db"   # وضع الجلسة، ليس -pooler
BETTER_AUTH_SECRET="<strong unique value>"
API_KEY_PEPPER="<strong unique value>"
CURSOR_HMAC_SECRET="<strong unique value>"
JWT_SECRET="<strong unique value>"
```

في `NODE_ENV=production` يرفض محمّل التهيئة التشغيل إذا بقي أي سر تطوير مخبوء. حافظ على ثبات `CURSOR_HMAC_SECRET`: تدويره يُبطل كل مؤشر ترقيم صفحي قائم.

## فحوص الصحة والجاهزية

تتوفر نقطتا نهاية منفصلتان:

| نقطة النهاية | تلمس PostgreSQL | الاستخدام |
| :--- | :--- | :--- |
| `GET /v1/health/live` | لا | حيوية الحاوية / استجابة حلقة الأحداث. |
| `GET /v1/health/ready` | نعم | جاهزية موازن التحميل. تُجري فحوص SQL حقيقية مقابل المستويين وكلتي جدولَي `schema_migrations` ونقطة LISTEN المخصصة؛ وتُرجع 503 عند فشل أي فحص. |

```bash
curl -fsS http://localhost:8080/v1/health/live
curl -fsS http://localhost:8080/v1/health/ready | jq '.ready, .status'
```

`/v1/health` هو اسم مستعار متوافق مهمل. يجب على المراقبين الجدد استخدام `/live` و`/ready`. وجّه بوابة الجاهزية في المنسّق إلى `/ready` حتى تُحجب حركة المرور إلى أن تصير الترحيلات وLISTEN سليمة.

## الترحيلات وRLS

- شغّل الترحيلات فقط عبر عناوين URL المباشرة غير المجمّعة أثناء CI/CD. يقارن فحص الجاهزية الترحيلات المطبَّقة والمجاميع مع الملفات على القرص؛ الترحيلات المفقودة أو المنحرفة تجعل الخدمة غير جاهزة.
- دور وقت التشغيل في مستوى البيانات هو مستخدم غير جذري (`vellum_runtime`). كل جدول مفعّل فيه Row-Level Security بسياسة عزل مستأجر تقرأ `app.current_project_id` .
- كل معاملة في مستوى البيانات تربط:

```sql
SET LOCAL statement_timeout = '5000ms';
SET LOCAL app.current_project_id = '<project_uuid>';
```

إذا حذف أي مسار كود سياق المستأجر، تُقيَّم `current_setting(..., true)` بـ `NULL` ويفشل PostgreSQL تلقائيًا (fail closed) بإرجاع صفوف صفرية. لا تتصل بمستوى البيانات كمستخدم جذري في الإنتاج أبدًا.

## عمال الخلفية

تأكد من تشغيل العمال الثلاثة المتكررين (idempotent): بناء الفهارس المركّبة (بدفعات 500)، وضغط صندوق البريد (تنظيف الأحداث الأقدم من 24 ساعة بدفعات 10,000)، وتنظيف علامات الحذف (حذف الصفوف المحذوفة ناعمًا بعد فترة الاحتفاظ، الافتراضي 7 أيام، بدفعات 5,000). بدون عامل البناء، تبقى الفهارس المُنشأة حديثًا في حالة `building` إلى الأبد.

## المراقبة والإخفاء

- استخدم مسجّل JSON المنظّم من `@vellum/observability`. يُصدر `requestId` و`projectId` و`projectId` و`durationMs`، ويُخفي تلقائيًا `pk_` و`sk_` و`Bearer ` و`secret_hash` وعناوين URL للاتصال.
- تحديد المعدل الافتراضي لكل مفتاح بنافذة منزلقة هو 100 RPS، ويُرجع `429 RATE_LIMITED` مع `Retry-After`.
- تكتب تعديلات مستوى التحكم مدخلات سجل تدقيق غير قابلة للتعديل. قد تُظهر واجهة الإدارة بيانات وصفية وحصصًا وصحة فهارس وسجلات تدقيق، لكن يجب ألا تعرض أبدًا حمولات `documents.data` الخاصة بالعملاء.

## النسخ الاحتياطي والاستعادة

- انسخ `control_db` و`data_db` كل على حدة؛ كلاهما مطلوب للاستعادة الكاملة.
- بما أن التهيئة الأولية تعتمد على `control_db` فقط، يمكنك استعادة المصادقة والتهيئة قبل استعادة مستندات العملاء.
- تدرّب على استعادة تتضمن اتساق `schema_migrations`؛ فحص الجاهزية يتحقق من انحراف الترحيلات عند كل تشغيل.
- يُحتفظ بصندوق البريد 24 ساعة؛ لا يمكن للعملاء استئناف الوقت الفعلي بعد هذه النافذة.

## تحذيرات معروفة

| التحذير | التوجيه |
| :--- | :--- |
| **لا Redis** | التخزين المؤقت وتحديد المعدل والإلغاء هي TTL داخل العملية إضافةً إلى حالة PostgreSQL؛ ويتم الإبطال عبر الحالات باستخدام `NOTIFY vellum_cache_invalidate`. لا تُدخل وسيط رسائل. |
| **زمن الاستجابة البعيد في Neon** | الرحلات ذهابًا وعودة عبر المناطق تزيد زمن المعاملات؛ ضع API بالقرب من قاعدة البيانات وأبقِ استدعاءات المعاملة قصيرة. |
| **LISTEN يحتاج وضع الجلسة** | نقطة `-pooler` في Neon لا تحمل `LISTEN`. وفّر `DATA_DATABASE_URL_LISTEN`، أو اقبل وقتًا فعليًا بالاستطلاع فقط (وظيفي لكنه أعلى زمنًا). |
| **Node ≥22** | بيئات التشغيل الأقدم غير مدعومة في الإنتاج. |
| **تدوير سر المؤشر** | يُبطل كل المؤشرات النشطة؛ خطّط لإعادة عملاء بدء الترقيم الصفحي. |
| **مستهلكو WebSocket البطيئون** | حد مخزن صادر 1 MiB يفصل المشتركين البطيئين (`SLOW_CONSUMER_DISCONNECT`). |
| **تأخر بناء الفهرس** | الفهارس المركّبة تبقى `building` حتى ينهي العامل عملها؛ استطلع الحالة قبل الاعتماد عليها. |

:::warning
لا تُخرج مفاتيح API أو رموز Bearer أو عناوين URL لقواعد البيانات في السجلات أو مخرجات CI. استخدم ملخّص التهيئة المُخفى (`getRedactedConfigSummary`) وعناصر نائبة مثل `<YOUR_API_KEY>` في الوثائق.
:::

## الأخطاء الشائعة

- **ترك قيمة تطوير افتراضية.** `NODE_ENV=production` يرفض التشغيل بالأسرار المخبوعة؛ استبدل قيم الأسرار الأربع كلها.
- **استخدام عنوان `-pooler` لـ `LISTEN`.** يُسقط LISTEN على مستوى الجلسة؛ استخدم `DATA_DATABASE_URL_LISTEN` بوضع الجلسة.
- **توجيه بوابة حركة المرور إلى `/health/live`.** لا يلمس PostgreSQL؛ وجّه بوابة الجاهزية إلى `/health/ready`.
- **الاتصال بمستوى البيانات كمستخدم جذري.** لن يفشل RLS تلقائيًا؛ استخدم الدور غير الجذري `vellum_runtime` واربط سياق المستأجر في كل معاملة.
