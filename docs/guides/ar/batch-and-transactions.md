# الكتابات الدفعية والمعاملات

يوفّر VELLUM طريقتين لتجميع الكتابات: `batchWrite` لمجموعة ذرية واحدة من التعديلات، و`runTransaction` لمنطق القراءة ثم الكتابة مع تحكم متفائل في التزامن (OCC).

## السيناريو

أنت تُهيّئ مستأجرًا جديدًا بمجموعة ثابتة معروفة من المستندات — كتابات يجب أن تنجح كلها أو لا شيء — لذا تستخدم `batchWrite`. ثم، عند تنفيذ تحويل بين حسابين تعتمد فيه الأرصدة الجديدة على قيم قرأتها أولًا، تستخدم `runTransaction` لتجنب فقدان التحديث.

```ts
const result = await db.batchWrite([
  { type: "create", path: "users/u_123", data: { name: "Ada", credits: 0 } },
  { type: "set", path: "users/u_123/stats", data: { logins: 0 }, merge: false },
  { type: "update", path: "counters/users", data: { total: fieldOp.increment(1) } },
  { type: "delete", path: "sessions/old_session" },
]);
```

## batchWrite

الحدود والدلالات:

| القيد | القيمة | الخطأ عند التجاوز |
| :--- | :--- | :--- |
| العمليات لكل دفعة | 100 | `BATCH_SIZE_EXCEEDED` (400) |
| الحمولة المتسلسلة | 5 MiB | `PAYLOAD_TOO_LARGE` (413) |

- يجب أن تكون الدفعة غير فارغة؛ مصفوفة `writes` الفارغة تُثير `INVALID_ARGUMENT`.
- تُنفَّذ كل التعديلات داخل **معاملة قاعدة بيانات واحدة**. أي فشل يُلغي الدفعة بأكملها — لا يوجد نجاح جزئي.
- تُتحقق التعديلات بالترتيب. فشل شرط `ifVersion` / `exists` يُثير `FAILED_PRECONDITION` (412)؛ وحذف مستند غير موجود يُثير `NOT_FOUND` (404)؛ وإنشاء مستند موجود يُثير `ALREADY_EXISTS` (409).
- الكتابات مرتين إلى المسار نفسه في دفعة واحدة تحافظ على دلالة القراءة بعد الكتابة عبر طبقة داخل الدفعة.
- كل تعديل ناجح يكتب حدث صندوق بريد في المعاملة نفسها، لذا يرى المشتركون الفعليون رؤية متسقة.

تحتوي النتيجة على نتيجة لكل تعديل بنفس ترتيب الكتابات المدخلة.

```ts
// مصفوفة النتيجة تُطابق الكتابات المدخلة حسب الفهرس.
for (const r of (result as { results: Array<{ path: string }> }).results) {
  console.log(r.path);
}
```

:::warning
الدفعة ذرية لكنها ليست دورة قراءة-تعديل-كتابة: لا يمكنك فحص القيمة الحالية لمستند في منتصف الدفعة. استخدم معاملة لذلك.
:::

## runTransaction (OCC)

تسمح المعاملة بقراءة المستندات وحساب قيم جديدة وإتمامها — مع ضمان عدم قيام كاتب آخر بتغيير مجموعة قراءتك في الفترة الفاصلة.

```ts
const { result, commit } = await db.runTransaction(
  async (tx) => {
    const from = await tx.get("accounts/a");
    const to = await tx.get("accounts/b");
    const amount = 50;
    tx.update("accounts/a", { balance: from.data().balance - amount });
    tx.update("accounts/b", { balance: to.data().balance + amount });
    return { moved: amount };
  },
  { maxAttempts: 5 }
);
```

كيف تعمل:

1. `POST .../transactions:begin` يُصدر `transactionToken` موقّعًا ويبدأ صفًا في جدول `transactions` بمستوى البيانات.
2. `tx.get()` يقرأ عبر الرمز؛ وتُسجَّل كل قراءة في مجموعة قراءات المعاملة مع الإصدار الملاحظ.
3. يُرتب استدعاؤك الكتابات (`create`, `set`, `update`, `delete`) دون إرسالها بعد.
4. `POST .../transactions:commit` يتحقق من صف المعاملة ويقفله و**كل مستند في مجموعة القراءات بترتيب `path ASC` الحتمي** باستخدام `SELECT ... FOR UPDATE`، ويقارن الإصدارات الملاحظة، ثم يطبّق كل الكتابات المُرتَّبة وأحداث صندوق البريد في معاملة PostgreSQL أصلية واحدة (`BEGIN` / `COMMIT` / `ROLLBACK`).

وبما أن حالة القفل تعيش في PostgreSQL، تتشارك عدة حالات من المحرك في حالة OCC — لا يوجد `Map` داخل العملية ولا خدمة قفل خارجية.

### إعادة المحاولة والتعارضات

إذا تغيّر مستند في مجموعة القراءات، يُرفض الإتمام بـ `ABORTED_CONFLICT` (409). يلتقط `runTransaction` هذا الخطأ تحديدًا ويعيد تشغيل الاستدعاء كاملًا مع تراجع أُسّي قصير (25–500 ms)، حتى `maxAttempts` (الافتراضي 5). أي خطأ آخر يُثار فورًا.

:::tip
أبقِ استدعاءات المعاملة صغيرة وخالية من التأثيرات الجانبية (لا استدعاءات شبكة، ولا إرسال رسائل بريد). قد يُشغَّل الاستدعاء أكثر من مرة عند حدوث تعارض.
:::

### المهلة

يجب أن تكتمل المعاملات خلال **5 ثوانٍ** (`MAX_TRANSACTION_DURATION_MS`). تجاوزها يُنتج `TRANSACTION_TIMEOUT` (408). العمل طويل الأمد لا مكان له في معاملة تفاعلية — احسب النتائج مسبقًا خارجها وأبقِ المعاملة قصيرة.

| الحد | القيمة | الخطأ |
| :--- | :--- | :--- |
| مدة المعاملة | 5,000 ms | `TRANSACTION_TIMEOUT` (408) |
| تعارض عند الإتمام | — | `ABORTED_CONFLICT` (409)، تُعاد محاولتها بواسطة SDK |

## الاختيار بينهما

- استخدم **batchWrite** عندما تعرف كل الكتابات مسبقًا ولا تعتمد على القيم الحالية.
- استخدم **runTransaction** عندما تعتمد القيم الجديدة على مستندات قرأتها (عدّادات، أرصدة، فحوص تفرد).
- استخدم `ifVersion` على كتابات [CRUD](./crud.md) الفردية عندما يكفي شرط مسبق لمستند واحد.

## الأخطاء الشائعة

- **القراءة في منتصف الدفعة.** لا يمكن لـ `batchWrite` فحص القيم الحالية؛ استخدم معاملة عندما تعتمد الكتابات على القراءات.
- **تأثيرات جانبية داخل استدعاء المعاملة.** قد يُشغَّل الاستدعاء عدة مرات عند التعارض؛ أبقِه نقيًا وخالًا من التأثيرات.
- **عمل طويل داخل معاملة.** الميزانية 5 ثوانٍ تُنتج `TRANSACTION_TIMEOUT`؛ احسب مسبقًا خارجها.
- **تجاوز حدود الدفعة.** أكثر من 100 عملية أو 5 MiB يُلغي الدفعة بأكملها دون نجاح جزئي.
