Core concepts / Composite Indexes

Composite Indexes#

Composite indexes accelerate queries that filter or sort on custom document fields. In a multi-tenant service, running CREATE INDEX per customer on the shared documents table would cause catalog bloat and DDL locks. VELLUM therefore stores indexes as rows, never as customer DDL.

Scenario#

Your reporting screen filters users by status and sorts by priority desc, and the query starts failing with FAILED_PRECONDITION and a suggestedIndex. You register that index with a server key, poll until its status is ready, and then the query runs as a single B-tree range scan.

How tenant indexes work#

TableRole
document_indexesIndex definition: collection path, ordered field list, definition hash, build status.
document_index_entriesOne row per document in the index, keyed by an order-preserving sort_key BYTEA.

An index definition names up to 3 fields, each with a path and a direction:

JSON
{
  "collectionPath": "users",
  "fields": [
    { "path": "status", "dir": "asc" },
    { "path": "priority", "dir": "desc" }
  ]
}

The sort key encodes each field value with a type-prefix byte (missing, null, boolean, numeric, string, timestamp, reference, bytes), then escapes delimiters so the key preserves the natural ordering of the logical values. For a desc field, every byte of that segment is inverted so a single ascending B-tree scan yields descending order. Because PostgreSQL compares BYTEA byte-by-byte, the primary key (index_id, sort_key, document_id) answers a multi-field range-and-sort query with one index scan.

Creation and status#

Indexes are managed with a server key holding the indexes:manage scope (public keys cannot manage indexes):

MethodEndpointPurpose
GET/v1/projects/:projectId/indexesList indexes and their statuses.
POST/v1/projects/:projectId/indexesRegister and backfill a new index.
DELETE/v1/projects/:projectId/indexes/:indexIdDelete an index and its entries.
BASH
curl -X POST "https://api.example.com/v1/projects/<PROJECT_ID>/indexes" \
  -H "x-project-key: <YOUR_SERVER_KEY>" \
  -H "content-type: application/json" \
  -d '{
    "collectionPath": "users",
    "fields": [
      { "path": "status", "dir": "asc" },
      { "path": "priority", "dir": "desc" }
    ]
  }'

Status values:

StatusMeaning
buildingRegistered; the backfill worker is populating entries.
readyFully built and used by the query planner.
failedBuild failed; errorMessage explains why.
deletingBeing removed.

The backfill worker claims building rows and scans active documents in deterministic batches of 500 ordered by document_id ASC, computing each sort_key and upserting entries until the index is ready. Subsequent writes maintain index entries transactionally.

NOTE

Registration returns immediately with status building. Poll GET .../indexes until the index is ready before relying on it for queries.

BASH
# Poll until the index is ready before depending on it in queries.
curl -s "https://api.example.com/v1/projects/<PROJECT_ID>/indexes" \
  -H "x-project-key: <YOUR_SERVER_KEY>" | jq '.indexes[] | {id, status, errorMessage}'

Duplicate creation (409)#

Index definitions are deduplicated by a hash of (project, collection path, fields) enforced by a unique database constraint. Creating an identical index returns ALREADY_EXISTS (409) with the existing collectionPath and definitionHash in the error details. Reuse the existing index instead of retrying.

When an index is needed#

  • No index needed: equality filters (==, in) and single-field ordering on built-in fields (documentId, createdAt, updatedAt) use built-in B-tree / GIN indexes.
  • Index needed: combining a range filter (<, <=, >, >=) with additional filters, or ordering by one or more custom document fields, requires a composite index.

If a query needs an index that does not exist, the server returns FAILED_PRECONDITION (412) with a suggestedIndex field list. Create that index, wait for ready, and retry. See Query.

WARNING

Each document's composite index entries count toward storage. Keep index definitions narrow — only the fields a real query needs — and delete unused indexes.

Common pitfalls#

  • Using a public key to manage indexes. Only a server key with indexes:manage can create or delete indexes.
  • Querying before the index is ready. Registration returns building; poll until ready first.
  • Retrying a duplicate index blindly. An identical definition returns ALREADY_EXISTS (409); reuse the existing index.
  • Indexing every field "just in case". Entries consume storage and slow writes; index only fields real queries use.

Verified example#

SDK / protocol
DART
import 'dart:io';
// Executed against the live PostgreSQL API by scripts/run-dart-examples.mjs.
//
// Composite indexes — a leaderboard index over (team, score).
// What you'll build: a tenant composite index created as a row via the REST
// API, an ordered query that uses it, then cleanup.
// Real-world scenario: ranking players by team and score needs a composite
// index, but no CREATE INDEX is ever issued on the shared documents table.
// `vellum_flutter` has no index helper, so `client.request` is used directly.
import 'package:vellum_flutter/vellum_flutter.dart';

Future<void> main() async {
  final endpoint = Platform.environment['VELLUM_API_BASE'] ??
      const String.fromEnvironment('VELLUM_API_BASE',
          defaultValue: 'http://127.0.0.1:8080');
  final projectId = Platform.environment['VELLUM_PROJECT_ID'] ??
      const String.fromEnvironment('VELLUM_PROJECT_ID');
  final apiKey = Platform.environment['VELLUM_API_KEY'] ??
      const String.fromEnvironment('VELLUM_API_KEY');

  final client =
      VellumClient(endpoint: endpoint, projectId: projectId, apiKey: apiKey);
  final prefix = 'ex_flutter_indexes_${DateTime.now().microsecondsSinceEpoch}';
  final col = client.collection(prefix);

  String? createdIndexId;
  try {
    print('=== Composite Indexes (Flutter) ===');
    for (final row in [
      {'id': 'p1', 'team': 'red', 'score': 10},
      {'id': 'p2', 'team': 'red', 'score': 30},
      {'id': 'p3', 'team': 'blue', 'score': 20},
    ]) {
      await col.doc(row['id'] as String).set(row);
    }

    final created = await client.request('POST', '/indexes', body: {
      'collectionPath': prefix,
      'fields': [
        {'path': 'team', 'dir': 'asc'},
        {'path': 'score', 'dir': 'asc'},
      ],
    });
    createdIndexId = created['id'] as String?;
    print('create: idReturned=${createdIndexId != null}');

    final listed = await client.request('GET', '/indexes');
    final indexes =
        (listed['indexes'] as List? ?? []).cast<Map<String, dynamic>>();
    print('listed: count=${indexes.length}');

    final rows = await col.where('team', '==', 'red').orderBy('score').get();
    print(
        'query ids=${rows.docs.map((d) => d.id).toList()} indexUsed=${rows.meta['indexUsed']}');
  } finally {
    if (createdIndexId != null) {
      try {
        await client.request('DELETE', '/indexes/$createdIndexId');
      } catch (_) {}
    }
    for (final id in ['p1', 'p2', 'p3']) {
      try {
        await col.doc(id).delete();
      } catch (_) {}
    }
    client.dispose();
  }
}

/**
 * Composite indexes — a leaderboard index over (team, score).
 *
 * What you'll build: a tenant-defined composite index that accelerates an
 * ordered leaderboard query.
 * Real-world scenario: ranking players by score within a team would otherwise
 * need a custom index. Tenant indexes are rows in document_indexes (never DDL
 * on the shared documents table), so creating one is safe in a shared cluster.
 * A repeated definition returns 409 ALREADY_EXISTS and is explicitly tolerated.
 */
import { harness, check } from "./_harness.js";

const h = await harness("indexes");
const col = h.prefix;
const fields = [
  { path: "team", dir: "asc" },
  { path: "score", dir: "asc" },
];

try {
  h.log("=== Composite Indexes ===");
  for (const row of [
    { id: "p1", team: "red", score: 10 },
    { id: "p2", team: "red", score: 30 },
    { id: "p3", team: "blue", score: 20 },
  ]) {
    await h.sdk.collection(col).doc(row.id).set(row);
  }

  const created = await h.api.data<{ id?: string }>("POST", "/indexes", {
    collectionPath: col,
    fields,
  });
  check(created.status === 201 || created.status === 409, "index creation is 201 or duplicate 409");
  const alreadyExists = created.status === 409;
  h.log({ createStatus: created.status, outcome: alreadyExists ? "already exists" : "created" });

  const listed = await h.api.data<{ indexes: Array<{ collectionPath: string; id: string }> }>("GET", "/indexes");
  check(listed.ok, "index listing succeeded");
  // The server returns the real (unscrubbed) path, so compare against `col`.
  const found = listed.body.indexes.find((index) => index.collectionPath === col);
  check(Boolean(found) || alreadyExists, "created index appears in the listing");
  h.log({ listed: listed.body.indexes.length > 0, foundInListing: Boolean(found) });

  const rows = await h.sdk.collection(col).where("team", "==", "red").orderBy("score", "asc").get();
  check(rows.docs.length === 2, "indexed query returned both red-team rows");
  h.log({
    query: "team == red ORDER BY score ASC",
    ids: rows.docs.map((doc) => doc.id),
    indexUsed: (rows.meta as { indexUsed?: string } | null)?.indexUsed,
  });

  if (found) {
    const removed = await h.api.data("DELETE", `/indexes/${found.id}`);
    check(removed.ok, "index deletion succeeded");
    h.log({ deleted: true });
  }
} finally {
  await h.cleanup();
}

 *
 * What you'll build: a tenant composite index created as a row via the REST
 * API, then an ordered query that uses it, then cleanup.

import { harness, check } from "./_harness.mjs";

const h = await harness("indexes");
const col = h.prefix;
const fields = [
  { path: "team", dir: "asc" },
  { path: "score", dir: "asc" },
];

try {
  h.log("=== Composite Indexes ===");
  for (const row of [
    { id: "p1", team: "red", score: 10 },
    { id: "p2", team: "red", score: 30 },
    { id: "p3", team: "blue", score: 20 },
  ]) {
    const res = await h.api.data("POST", `/documents/${col}/${row.id}`, { data: row });
    check(res.status === 201, `seed player ${row.id}`);
  }

  const created = await h.api.data("POST", "/indexes", { collectionPath: col, fields });
  check(created.status === 201 || created.status === 409, "index creation is 201 or duplicate 409");
  const alreadyExists = created.status === 409;
  h.log({ createStatus: created.status, outcome: alreadyExists ? "already exists" : "created" });

  const listed = await h.api.data("GET", "/indexes");
  check(listed.ok, "index listing succeeded");
  const found = listed.body.indexes.find((index) => index.collectionPath === col);
  check(Boolean(found) || alreadyExists, "created index appears in the listing");
  h.log({ listed: listed.body.indexes.length > 0, foundInListing: Boolean(found) });

  const rows = await h.api.data("POST", "/query", {
    collectionPath: col,
    where: [{ field: "team", op: "==", value: "red" }],
    orderBy: [{ field: "score", dir: "asc" }],
    limit: 50,
    select: null,
    startAt: null,
    startAfter: null,
  });
  const ids = rows.body.documents.map((d) => d.documentId);
  check(rows.ok && ids.length === 2, "indexed query returned both red-team rows");
  h.log({
    query: "team == red ORDER BY score ASC",
    ids,
    indexUsed: rows.body.meta?.indexUsed,
  });

  if (found) {
    const removed = await h.api.data("DELETE", `/indexes/${found.id}`);
    check(removed.ok, "index deletion succeeded");
    h.log({ deleted: true });

  await h.cleanup();
}
