Security / Security Rules

Security Rules#

Security rules decide whether a public API key (pk_) may read or write a document. They are stored as a versioned JSON Abstract Syntax Tree in the control plane and evaluated synchronously in memory — never by generating or executing code.

NOTE

Server keys (sk_) bypass the rules AST for operations covered by their scopes. Public keys always evaluate rules; with no active ruleset, access is denied.

Scenario#

You run a multi-user app where each user may read and write only their own users/{userId} document, while a small admin group may read all users. You publish a ruleset that binds ownership to the path wildcard, check it in the Rule Simulator, and verify that an unauthorized pk_ request gets PERMISSION_DENIED.

Ruleset shape (v1)#

JSON
{
  "version": 1,
  "rules": [
    {
      "match": "users/{userId}",
      "allow": {
        "get": { "op": "==", "left": { "var": "auth.uid" }, "right": { "var": "path.userId" } },
        "list": { "op": "==", "left": { "var": "auth.claims.role" }, "right": { "val": "admin" } },
        "create": {
          "op": "all",
          "conditions": [
            { "op": "==", "left": { "var": "auth.uid" }, "right": { "var": "path.userId" } },
            { "op": "==", "left": { "var": "request.data.ownerId" }, "right": { "var": "auth.uid" } }
          ]
        },
        "update": { "op": "==", "left": { "var": "resource.data.ownerId" }, "right": { "var": "auth.uid" } },
        "delete": { "op": "==", "left": { "var": "auth.claims.role" }, "right": { "val": "admin" } }
      }
    }
  ]
}

version must be 1 and rules must be an array. Each rule has a match path pattern and an allow object whose keys are operations: get, list, create, update, delete, plus the shorthands read (covers get/list) and write (covers create/update/delete).

Wildcard matching#

  • {paramName} binds one segment to path.<paramName>.
  • {document=**} at the end of a pattern matches one or more remaining segments and binds the relative sub-path to path.document.
  • If several rules match a path, access is granted when any matching rule evaluates to true for the operation (standard OR semantics). No match, or no true expression, means deny.

Expression operators#

CategoryOperators
Comparisons==, !=, <, <=, >, >=, in
Object / typehasKey, isType
Combinatorsall (every conditions), any (some conditions), not (one condition)

Operands are either { "val": ... } for a literal or { "var": "..." } for a context value:

VariableMeaning
auth.uidEnd-user id from the bearer JWT (null without a token).
auth.claims.<path>Claim from the end-user JWT.
path.<param>Value bound by a wildcard in match.
resource.data[.<path>]Existing document data (null on create).
request.data[.<path>]Incoming document data (null on reads/deletes).
request.timeRequest timestamp in epoch milliseconds.

All comparisons use the same typed wire-value equality and ordering as the query engine.

Deterministic evaluation and bounds#

  • Evaluation is 100% synchronous and in memory: no dynamic code execution, no network calls, and no recursive I/O. Complex expressions cannot turn a request into a denial-of-service vector.
  • Validation enforces max AST depth 10 and max 100 nodes per rule expression. Exceeding either raises QUERY_TOO_COMPLEX.
  • Circular references are rejected at validation time, and unknown operators or operands evaluate to false (deny).
  • Deny by default: authorizeOperation throws PERMISSION_DENIED (403) unless a matching rule explicitly allows the operation.
WARNING

Rules are validated against the v1 schema at publish time. A malformed AST (bad version, missing match/allow, unsupported operation or operator) is rejected with INVALID_ARGUMENT before it can become active.

Publishing and simulation#

Publish through the session-authenticated console API:

MethodEndpointPurpose
POST/v1/projects/:projectId/rulesetsValidate and publish a new version; writes an audit log and invalidates caches.
GET/v1/projects/:projectId/rulesetsRead the active ruleset (or the built-in default when none is published).
BASH
curl -X POST "https://api.example.com/v1/projects/<PROJECT_ID>/rulesets" \
  -H "Authorization: Bearer <SESSION_TOKEN>" \
  -H "content-type: application/json" \
  -d '{ "rulesAst": { "version": 1, "rules": [ /* ... */ ] } }'

Publishing immediately affects the project: the ruleset cache is invalidated locally and across instances via NOTIFY vellum_cache_invalidate. For a dry run before publishing, the dashboard's Rule Simulator evaluates a candidate AST against a simulated auth and path context and reports whether the request would be allowed and which rule matched. You can also validate a candidate against the project using a public key.

Least privilege patterns#

JSON
{
  "match": "users/{userId}/orders/{orderId}",
  "allow": {
    "get": { "op": "==", "left": { "var": "auth.uid" }, "right": { "var": "path.userId" } },
    "create": {
      "op": "all",
      "conditions": [
        { "op": "==", "left": { "var": "auth.uid" }, "right": { "var": "path.userId" } },
        { "op": "isType", "left": { "var": "request.data.total" }, "right": { "val": "number" } }
      ]
    }
  }
}

Bind the owner id to a path wildcard rather than trusting a client-supplied field, and check resource.data on updates so ownership cannot be transferred by a malicious patch.

Common pitfalls#

  • Trusting a client-supplied owner field. Bind ownership to a path wildcard and verify it against auth.uid.
  • Allowing updates without checking resource.data. A malicious patch could transfer ownership if you only validate the incoming data.
  • Forgetting deny-by-default. If no rule matches, access is denied — publish the ruleset and confirm the shape (version: 1).
  • Overly deep or large rulesets. Exceeding depth 10 or 100 nodes per expression raises QUERY_TOO_COMPLEX at publish time.

Verified example#

SDK / protocol
DART
import 'dart:io';
// Executed by scripts/run-dart-examples.mjs against a PostgreSQL API.
//
// Security rules AST — publish a deny-by-default v1 ruleset.
// What you'll build: a versioned ruleset with one explicit scoped allow, then
// verification, rejection of a malformed AST, and restoration.
// Real-world scenario: locking down a collection means allowing only the
// listed operations; everything else is denied by default. Console endpoints
// live outside the data-plane baseUrl, so `client.httpTransport` is used with a
// session bearer token. Credentials are injected via --dart-define, never hard-coded.
import 'package:vellum_flutter/vellum_flutter.dart';

Future<void> main() async {
  final endpoint = Platform.environment['VELLUM_API_BASE'] ??
      const String.fromEnvironment('VELLUM_API_BASE',
          defaultValue: 'http://127.0.0.1:8080');
  final projectId = Platform.environment['VELLUM_PROJECT_ID'] ??
      const String.fromEnvironment('VELLUM_PROJECT_ID');
  final apiKey = Platform.environment['VELLUM_API_KEY'] ??
      const String.fromEnvironment('VELLUM_API_KEY');
  final email = Platform.environment['VELLUM_EMAIL'] ??
      const String.fromEnvironment('VELLUM_EMAIL');
  final password = Platform.environment['VELLUM_PASSWORD'] ??
      const String.fromEnvironment('VELLUM_PASSWORD');

  final client =
      VellumClient(endpoint: endpoint, projectId: projectId, apiKey: apiKey);
  final prefix = 'ex_flutter_rules_${DateTime.now().microsecondsSinceEpoch}';
  final rulesUrl = '$endpoint/v1/console/projects/$projectId/rulesets';

  final signIn = await client.httpTransport(
    'POST',
    '$endpoint/v1/auth/sign-in/email',
    {'Content-Type': 'application/json'},
    {'email': email, 'password': password},
  );
  final login = objectMap(signIn, 'sign-in');
  if (login['token'] is! String) throw StateError('Missing sign-in token');
  final headers = {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer ${login['token']}',
  };

  final original = await client.httpTransport('GET', rulesUrl, headers, null);
  final originalMap = objectMap(original, 'ruleset');
  final originalAst = originalMap['rulesAst'] ?? {'version': 1, 'rules': []};
  final beforeVersion = (originalMap['version'] as num?) ?? 0;

  try {
    print('=== Security Rules AST (Flutter) ===');
    print('before: hasRuleset=${beforeVersion > 0}');

    // Deny by default: only a scoped read and a conditional create are granted.
    final ast = {
      'version': 1,
      'rules': [
        {
          'match': '$prefix/{docId}',
          'allow': {
            'read': true,
            'create': {
              'op': '==',
              'left': {'var': 'request.data.team'},
              'right': {'val': 'red'}
            },
          },
        },
      ],
    };
    final published = await client
        .httpTransport('POST', rulesUrl, headers, {'rulesAst': ast});
    print(
        'publish: versionAdvancedBy=${(objectMap(published, 'published ruleset')['version'] as num) - beforeVersion}');

    final active = await client.httpTransport('GET', rulesUrl, headers, null);
    final activeMap = objectMap(active, 'active ruleset');
    final rulesValue = objectMap(activeMap['rulesAst'], 'rules AST')['rules'];
    if (rulesValue is! List || rulesValue.isEmpty)
      throw StateError('Expected non-empty rules');
    final allow =
        objectMap(objectMap(rulesValue.first, 'rule')['allow'], 'allow');
    print(
        'activeVersion=${activeMap['version']} operations=${allow.keys.toList()}');

    try {
      await client.httpTransport('POST', rulesUrl, headers, {
        'rulesAst': {'version': 2, 'rules': []}
      });
    } on VellumException catch (e) {
      print('invalidAst: code=${e.code} status=${e.statusCode}');
    }
  } finally {
    try {
      await client
          .httpTransport('POST', rulesUrl, headers, {'rulesAst': originalAst});
    } finally {
      client.dispose();
    }
  }
}

Map<String, dynamic> objectMap(Object? value, String context) {
  if (value is VellumHttpResponse) value = value.body;
  if (value is! Map<String, dynamic>)
    throw FormatException('Expected object: $context');
  return value;
}

TS✓ VERIFIED SOURCE
/**
 * Security rules AST — publish a deny-by-default v1 ruleset.
 *
 * What you'll build: a versioned ruleset that grants exactly one scoped
 * permission (read plus a conditional create) and denies everything else.
 * Real-world scenario: locking down a new collection means publishing a rule
 * whose only `allow` clauses are explicit; any operation not matched is denied
 * by default. The example verifies the active version, rejects a malformed AST,
 * and restores the original ruleset in `finally` so no policy change leaks.
 */
import { harness, check } from "./_harness.js";

const h = await harness("rules");
const rulesPath = `/projects/${h.projectId}/rulesets`;
const original = await h.api.console<{ rulesAst?: unknown }>("GET", rulesPath);
let originalAst: unknown = original.body.rulesAst ?? { version: 1, rules: [] };

try {
  h.log("=== Security Rules AST ===");
  const beforeVersion = (original.body as { version?: number }).version ?? 0;
  h.log({
    before: {
      hasRuleset: beforeVersion > 0,
      ruleCount: Array.isArray((original.body as { rulesAst?: { rules?: unknown[] } }).rulesAst?.rules)
        ? (original.body as { rulesAst: { rules: unknown[] } }).rulesAst.rules.length
        : 0,
    },
  });

  // Deny by default: only `read` and a conditional `create` are allowed for
  // this one collection. update/delete (and all other paths) are not listed.
  const ast = {
    version: 1,
    rules: [
      {
        match: `${h.prefix}/{docId}`,
        allow: {
          read: true,
          create: {
            op: "==",
            left: { var: "request.data.team" },
            right: { val: "red" },
          },
        },
      },
    ],
  };
  const published = await h.api.console("POST", rulesPath, { rulesAst: ast });
  check(published.status === 201, "valid AST publishes with HTTP 201");
  const publishedBody = published.body as { id: string; version: number };
  h.log({ publish: "ok", versionAdvancedBy: publishedBody.version - beforeVersion, ruleCount: ast.rules.length });

  const active = await h.api.console<{
    version: number;
    rulesAst: { version: number; rules: Array<{ match: string; allow: Record<string, unknown> }> };
  }>("GET", rulesPath);
  check(active.body.rulesAst.rules.length === 1, "published rule is the active ruleset");
  check(active.body.version >= publishedBody.version, "active version did not regress");
  h.log({
    activeVersionMatchesPublished: active.body.version === publishedBody.version,
    astVersion: active.body.rulesAst.version,
    match: active.body.rulesAst.rules[0]?.match,
    operations: Object.keys(active.body.rulesAst.rules[0]?.allow ?? {}),
  });

  const invalid = await h.api.console("POST", rulesPath, { rulesAst: { version: 2, rules: [] } });
  const invalidCode = (invalid.body as { error?: { code?: string } })?.error?.code;
  check(invalid.status === 400 && invalidCode === "INVALID_ARGUMENT", "unsupported AST version is rejected");
  h.log({ invalidAst: { status: invalid.status, code: invalidCode } });
} finally {
  try {
    await h.api.console("POST", rulesPath, { rulesAst: originalAst });
  } catch {
    // Best effort restoration.
  }
  await h.cleanup();
}
