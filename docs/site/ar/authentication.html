البداية / المصادقة

المصادقة#

تُعزل بيانات اعتماد VELLUM تمامًا لكل سطح. تتشارك الأسطح في عناصر التشفير عديمة الحالة فقط، بينما التخزين ومفاتيح التوقيع وtyp/iss/aud والوسيط منفصلة تمامًا — يُرفض أي رمز أُنشئ لسطح في أي سطح آخر.

مستوى المستندات (/v1/projects/...) يستخدم مفاتيح API عبر x-vellum-api-key (والاسم القديم x-project-key) مع رمز مستخدم نهائي اختياري بخوارزمية EdDSA فقط. لا يوجد بديل HS256 ولا وضع مجهول ولا مفتاح رئيسي ضمني.

راجع مصادقة المستخدمين النهائيين للرموز وتدوير التحديث ومرجع REST وتحديد المعدل.

NOTE

يمكن أن يظهر مفتاح API عام بأمان في متصفح أو تطبيق جوال، لكنه يمنح صفر وصول ضمني للبيانات. تُقيَّم كل عملية مقابل مجموعة قواعد الأمان النشطة في البيئة. أما مفتاح الخادم فتتجاوز القواعد فقط للنطاقات التي يحملها صراحةً.

السيناريو#

أنت تضيف ميزة حيث يسجّل المستخدمون الدخول إلى تطبيقك ويقرأ العميل مستنداته الخاصة فقط. تُصدر مفتاح pk_ عامًا للمتصفح، وتُرفق JWT الخاص بالمستخدم المسجّل بكل طلب، وتعتمد على قواعد الأمان لفرض الملكية — مع إبقاء المفتاح الرئيسي sk_ على خادمك فقط.

BASH
# كل استدعاء لمستوى المستندات يقدّم المفتاح في ترويسة، وليس في URL.
curl "https://api.example.com/v1/projects/<PROJECT_ID>/documents/users/u_123" \
  -H "x-project-key: <YOUR_PUBLIC_KEY>" \
  -H "Authorization: Bearer <END_USER_JWT>"

مفاتيح API (pk_ / sk_)#

تُنشأ المفاتيح بالشكل <prefix>_<envTag>_<random>:

البادئةالنوعطول الجسموسم البيئة
pk_عام32 حرفًا base62live (القديم dev / stg لا يزال صالحًا)
sk_خادم48 حرفًا base62live (القديم dev / stg لا يزال صالحًا)

أمثلة على الشكل فقط (قيم غير قابلة للاستخدام): pk_... وsk_.... المفاتيح هي pk_/sk_ ومقيدة بالمشروع فقط.

يُحفظ فقط بادئة من 16 حرفًا وتجزئة (digest). التجزئة هي SHA256(fullKey + ":" + API_KEY_PEPPER) وتُقارن بزمن ثابت. يُعرض المفتاح الصريح مرة واحدة فقط عند الإنشاء. تُخزَّن المفاتيح المتحقق منها في ذاكرة العملية لمدة 30 ثانية؛ وينشر الإلغاء والتدوير الإشعار NOTIFY vellum_cache_invalidate حتى تتخلص الحالات الأخرى من مدخلاتها المخزنة.

النطاقات (scopes)#

يحمل مفتاح الخادم نطاقات صريحة. النطاق المطلوب حسب العملية:

العمليةالنطاق المطلوب
get, list, querydocuments:read
create, set, update, delete, batchWrite, والمعاملاتdocuments:write
إدارة الفهارسindexes:manage

النطاق * يمنح كل شيء. لا يمكن للمفتاح العام إدارة الفهارس المركّبة. غياب النطاق يُنتج PERMISSION_DENIED (403)؛ وغياب المفتاح أو بطلانه يُنتج UNAUTHENTICATED (401).

TS
import { createClient } from "@vellumdb/sdk-js";

const db = createClient({
  endpoint: "https://api.example.com",
  projectId: "<YOUR_PROJECT_ID>",
  apiKey: "<YOUR_API_KEY>", // يُرسل كـ x-project-key
  getAuthToken: async () => currentUserJwt(), // رمز المستخدم النهائي اختياري لـ auth.uid
});

رموز المستخدمين النهائيين وتقييم القواعد#

عند استخدام مفتاح عام، يوفّر الترويسة الاختيارية Authorization: Bearer <jwt> هوية المستخدم النهائي. يُقدّم استدعاء getAuthToken في SDK هذا الرمز مع كل طلب. يمكن لشجرة القواعد قراءة auth.uid وauth.claims.<field>، لذا يمكن لمفتاح عام واحد أن يخدم عدة مستخدمين بأمان. راجع قواعد الأمان.

التدوير والإلغاء#

تُصدر المفاتيح لكل مشروع. يُعرض المفتاح الخام مرة واحدة فقط عند إنشائه؛ وبعدها تُعرض فقط البادئات والنطاقات والحالة وبيانات الاستخدام.

للتدوير دون توقف: أنشئ المفتاح الجديد، ثم انشره على العملاء، وتأكد من تحوّل حركة المرور، ثم ألغِ المفتاح القديم. وبما أن الإلغاء يُفرض مقابل سجل مستوى التحكم أيضًا، فلا يمكن استخدام مفتاح مخزّن مؤقتًا بعد ضبط revokedAt له.

أقل قدر من الامتيازات#

  • استخدم مفاتيح منفصلة لكل مشروع، ولا تعد استخدام مفتاح مشروع في مشروع آخر. لكل مشروع بيئة قياسية واحدة، لذا فإن الأسماء القديمة والمفاتيح هي مرادفات للبيئة نفسها وليست مراحل نشر منفصلة.
  • فضّل مفاتيح pk_ في تطبيقات العميل واترك لقواعد الأمان تحديد الوصول؛ واستخدم مفاتيح sk_ على الخوادم الموثوقة فقط.
  • امنح أضيق مجموعة نطاقات: الخدمات للقراءة فقط تحصل على documents:read، وأدوات الفهارس تحصل على indexes:manage.
  • حدّد تاريخ انتهاء للمفاتيح المؤقتة ودوّرها بشكل دوري.
WARNING

لا تسجّل أبدًا مفاتيح pk_/sk_ الخام أو رموز Bearer JWT أو عناوين URL لقواعد البيانات. يُخفي مسجّل البنية في @vellum/observability هذه الأنماط تلقائيًا؛ أبقِ جميع سجلات التطبيق على هذا المسار.

الأخطاء الشائعة#

  • الخلط بين بيانات الاعتماد. أي اعتماد أُنشئ خارج مستوى المستندات يُرفض عليه، ومفتاح API لا يخوّل شيئًا خارجه.
  • افتراض أن المفتاح العام مميز. بدون مجموعة قواعد نشطة، يُرفض الوصول بالمفتاح العام؛ يجب أن تسمح القواعد صراحةً بكل عملية.
  • استخدام نطاق * للراحة. مفتاح الخادم واسع النطاق يُفقد مبدأ أقل قدر من الامتيازات؛ امنح فقط ما تحتاجه الخدمة.
  • نسيان التدوير. أنشئ البديل أولًا، ثم انقل العملاء، ثم ألغِ القديم — لا تُلغِ قبل نشر المفتاح الجديد.

ماذا تقرأ بعد ذلك#

  • مصادقة المستخدمين النهائيين — عزل بيانات الاعتماد، تدوير التحديث، إسقاط الملف، مصادقة WebSocket وتحديد المعدل.
  • مجموعة JavaScript · مجموعة Flutter — واجهة المصادقة والتحديث الصامت في العميلين.
  • قواعد الأمان — شجرة AST التي تُقيَّم افتراضيًا بالرفض للمفاتيح العامة.
  • REST API — كيف يُرسل المفتاح في كل نقطة نهاية.
  • قائمة التحقق للإنتاج — بوابات الإصدار ونظافة الأسرار.
