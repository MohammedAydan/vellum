الفهارس المركّبة#

تُسرّع الفهارس المركّبة الاستعلامات التي تُصفّي أو تُرتّب على حقول مستندات مخصصة. في خدمة متعددة المستأجرين، يُسبب تشغيل CREATE INDEX لكل عميل على جدول documents المشترك تضخمًا في دليل النظام وأقفال DDL. لذلك يخزّن VELLUM الفهارس كـ صفوف، لا كأوامر DDL خاصة بالعملاء.

السيناريو#

تبدأ شاشة التقارير بتصفية المستخدمين حسب status وترتيبهم حسب priority desc، فيفشل الاستعلام بـ FAILED_PRECONDITION ومعه suggestedIndex. تُسجّل هذا الفهرس بمفتاح خادم، وتستطلع حالته حتى تصير ready، ثم يعمل الاستعلام كمسح نطاق واحد على شجرة B.

كيف تعمل فهارس المستأجرين#

الجدولالدور
document_indexesتعريف الفهرس: مسار المجموعة، وقائمة الحقول المرتبة، وتجزئة التعريف، وحالة البناء.
document_index_entriesصف واحد لكل مستند داخل الفهرس، مفتاحه sort_key BYTEA يحافظ على الترتيب.

يحدد تعريف الفهرس حتى 3 حقول، لكل منها مسار واتجاه:

JSON
{
  "collectionPath": "users",
  "fields": [
    { "path": "status", "dir": "asc" },
    { "path": "priority", "dir": "desc" }
  ]
}

يُرمّز مفتاح الفرز كل قيمة حقل ببايت بادئة نوع (مفقود، null، منطقي، رقمي، نص، طابع زمني، مرجع، بايتات)، ثم يهرب الفواصل حتى يحافظ المفتاح على الترتيب الطبيعي للقيم المنطقية. أما الحقل desc فتُقلب كل بايتات مقطعه ليُنتج مسح B-tree تصاعدي واحد الترتيب التنازلي. وبما أن PostgreSQL يقارن BYTEA بايتًا ببايت، يجيب المفتاح الأساسي (index_id, sort_key, document_id) عن استعلام نطاق وترتيب متعدد الحقول بـ مسح فهرس واحد.

الإنشاء والحالة#

تُدار الفهارس بمفتاح خادم يحمل نطاق indexes:manage (لا يمكن للمفاتيح العامة إدارة الفهارس):

الطريقةنقطة النهايةالغرض
GET/v1/projects/:projectId/indexesعرض الفهارس وحالاتها.
POST/v1/projects/:projectId/indexesتسجيل فهرس جديد وبناؤه.
DELETE/v1/projects/:projectId/indexes/:indexIdحذف فهرس وإدخالاته.
BASH
curl -X POST "https://api.example.com/v1/projects/<PROJECT_ID>/indexes" \
  -H "x-project-key: <YOUR_SERVER_KEY>" \
  -H "content-type: application/json" \
  -d '{
    "collectionPath": "users",
    "fields": [
      { "path": "status", "dir": "asc" },
      { "path": "priority", "dir": "desc" }
    ]
  }'

قيم الحالة:

الحالةالمعنى
buildingمُسجَّل؛ عامل البناء (backfill) يشغّل الإدخالات.
readyمكتمل البناء ويستخدمه مخطّط الاستعلام.
failedفشل البناء؛ يشرح errorMessage السبب.
deletingقيد الإزالة.

يستحوذ عامل البناء على صفوف building ويمسح المستندات النشطة بدفعات حتمية من 500 مرتبة بـ document_id ASC، ويحسب كل sort_key ويرفع الإدخالات حتى يصير الفهرس ready. وتحافظ الكتابات اللاحقة على إدخالات الفهرس داخل المعاملة.

NOTE

يُرجع التسجيل فورًا بالحالة building. استطلع GET .../indexes حتى يصير الفهرس ready قبل الاعتماد عليه في الاستعلامات.

BASH
# استطلع حتى يصير الفهرس ready قبل الاعتماد عليه في الاستعلامات.
curl -s "https://api.example.com/v1/projects/<PROJECT_ID>/indexes" \
  -H "x-project-key: <YOUR_SERVER_KEY>" | jq '.indexes[] | {id, status, errorMessage}'

الإنشاء المكرر (409)#

تُخفَّض تعريفات الفهارس إلى تجزئة لـ (project, collection path, fields) يفرضها قيد فريد في قاعدة البيانات. يُرجع إنشاء فهرس مطابق ALREADY_EXISTS (409) مع collectionPath وdefinitionHash الحاليين في تفاصيل الخطأ. أعد استخدام الفهرس الموجود بدلًا من إعادة المحاولة.

متى يُطلب فهرس#

  • لا فهرس مطلوب: مرشحات المساواة (==, in) والترتيب على حقل واحد من الحقول المدمجة (documentId, createdAt, updatedAt) تستخدم فهارس B-tree / GIN المدمجة.
  • فهرس مطلوب: الجمع بين مرشح نطاق (<, <=, >, >=) ومرشحات إضافية، أو الترتيب بحقل مستند مخصص واحد أو أكثر، يتطلب فهرسًا مركّبًا.

إذا احتاج استعلام فهرسًا غير موجود، يُرجع الخادم FAILED_PRECONDITION (412) مع قائمة حقول suggestedIndex. أنشئ ذلك الفهرس، وانتظر ready، ثم أعد المحاولة. راجع الاستعلام.

WARNING

تُحتسب إدخالات الفهارس المركّبة لكل مستند ضمن التخزين. أبقِ تعريفات الفهارس ضيقة — الحقول التي يحتاجها استعلام حقيقي فقط — واحذف الفهارس غير المستخدمة.

الأخطاء الشائعة#

  • استخدام مفتاح عام لإدارة الفهارس. فقط مفتاح الخادم الذي يحمل indexes:manage يمكنه إنشاء الفهارس أو حذفها.
  • الاستعلام قبل أن يصير الفهرس ready. التسجيل يُرجع building؛ استطلع حتى ready أولًا.
  • إعادة محاولة فهرس مكرر عشوائيًا. التعريف المطابق يُرجع ALREADY_EXISTS (409)؛ أعد استخدام الفهرس الحالي.
  • فهرسة كل حقل «تحسبًا». الإدخالات تستهلك التخزين وتُبطئ الكتابات؛ فهرس فقط الحقول التي تستخدمها استعلامات فعلية.

مثال موثّق#

المجموعة / البروتوكول
DART
import 'dart:io';
// Executed against the live PostgreSQL API by scripts/run-dart-examples.mjs.
//
// Composite indexes — a leaderboard index over (team, score).
// What you'll build: a tenant composite index created as a row via the REST
// API, an ordered query that uses it, then cleanup.
// Real-world scenario: ranking players by team and score needs a composite
// index, but no CREATE INDEX is ever issued on the shared documents table.
// `vellum_flutter` has no index helper, so `client.request` is used directly.
import 'package:vellum_flutter/vellum_flutter.dart';

Future<void> main() async {
  final endpoint = Platform.environment['VELLUM_API_BASE'] ??
      const String.fromEnvironment('VELLUM_API_BASE',
          defaultValue: 'http://127.0.0.1:8080');
  final projectId = Platform.environment['VELLUM_PROJECT_ID'] ??
      const String.fromEnvironment('VELLUM_PROJECT_ID');
  final apiKey = Platform.environment['VELLUM_API_KEY'] ??
      const String.fromEnvironment('VELLUM_API_KEY');

  final client =
      VellumClient(endpoint: endpoint, projectId: projectId, apiKey: apiKey);
  final prefix = 'ex_flutter_indexes_${DateTime.now().microsecondsSinceEpoch}';
  final col = client.collection(prefix);

  String? createdIndexId;
  try {
    print('=== Composite Indexes (Flutter) ===');
    for (final row in [
      {'id': 'p1', 'team': 'red', 'score': 10},
      {'id': 'p2', 'team': 'red', 'score': 30},
      {'id': 'p3', 'team': 'blue', 'score': 20},
    ]) {
      await col.doc(row['id'] as String).set(row);
    }

    final created = await client.request('POST', '/indexes', body: {
      'collectionPath': prefix,
      'fields': [
        {'path': 'team', 'dir': 'asc'},
        {'path': 'score', 'dir': 'asc'},
      ],
    });
    createdIndexId = created['id'] as String?;
    print('create: idReturned=${createdIndexId != null}');

    final listed = await client.request('GET', '/indexes');
    final indexes =
        (listed['indexes'] as List? ?? []).cast<Map<String, dynamic>>();
    print('listed: count=${indexes.length}');

    final rows = await col.where('team', '==', 'red').orderBy('score').get();
    print(
        'query ids=${rows.docs.map((d) => d.id).toList()} indexUsed=${rows.meta['indexUsed']}');
  } finally {
    if (createdIndexId != null) {
      try {
        await client.request('DELETE', '/indexes/$createdIndexId');
      } catch (_) {}
    }
    for (final id in ['p1', 'p2', 'p3']) {
      try {
        await col.doc(id).delete();
      } catch (_) {}
    }
    client.dispose();
  }
}

/**
 * Composite indexes — a leaderboard index over (team, score).
 *
 * What you'll build: a tenant-defined composite index that accelerates an
 * ordered leaderboard query.
 * Real-world scenario: ranking players by score within a team would otherwise
 * need a custom index. Tenant indexes are rows in document_indexes (never DDL
 * on the shared documents table), so creating one is safe in a shared cluster.
 * A repeated definition returns 409 ALREADY_EXISTS and is explicitly tolerated.
 */
import { harness, check } from "./_harness.js";

const h = await harness("indexes");
const col = h.prefix;
const fields = [
  { path: "team", dir: "asc" },
  { path: "score", dir: "asc" },
];

try {
  h.log("=== Composite Indexes ===");
  for (const row of [
    { id: "p1", team: "red", score: 10 },
    { id: "p2", team: "red", score: 30 },
    { id: "p3", team: "blue", score: 20 },
  ]) {
    await h.sdk.collection(col).doc(row.id).set(row);
  }

  const created = await h.api.data<{ id?: string }>("POST", "/indexes", {
    collectionPath: col,
    fields,
  });
  check(created.status === 201 || created.status === 409, "index creation is 201 or duplicate 409");
  const alreadyExists = created.status === 409;
  h.log({ createStatus: created.status, outcome: alreadyExists ? "already exists" : "created" });

  const listed = await h.api.data<{ indexes: Array<{ collectionPath: string; id: string }> }>("GET", "/indexes");
  check(listed.ok, "index listing succeeded");
  // The server returns the real (unscrubbed) path, so compare against `col`.
  const found = listed.body.indexes.find((index) => index.collectionPath === col);
  check(Boolean(found) || alreadyExists, "created index appears in the listing");
  h.log({ listed: listed.body.indexes.length > 0, foundInListing: Boolean(found) });

  const rows = await h.sdk.collection(col).where("team", "==", "red").orderBy("score", "asc").get();
  check(rows.docs.length === 2, "indexed query returned both red-team rows");
  h.log({
    query: "team == red ORDER BY score ASC",
    ids: rows.docs.map((doc) => doc.id),
    indexUsed: (rows.meta as { indexUsed?: string } | null)?.indexUsed,
  });

  if (found) {
    const removed = await h.api.data("DELETE", `/indexes/${found.id}`);
    check(removed.ok, "index deletion succeeded");
    h.log({ deleted: true });
  }
} finally {
  await h.cleanup();
}

 * Composite indexes (REST) — a leaderboard index over (team, score).
 *
 * What you'll build: a tenant composite index created as a row via the REST
 * API, then an ordered query that uses it, then cleanup.
 * Real-world scenario: ranking players by team and score needs a composite
 * index, but no CREATE INDEX on the shared documents table is ever issued.
 */
import { harness, check } from "./_harness.mjs";

const h = await harness("indexes");
const col = h.prefix;
const fields = [
  { path: "team", dir: "asc" },
  { path: "score", dir: "asc" },
];

try {
  h.log("=== Composite Indexes ===");
  for (const row of [
    { id: "p1", team: "red", score: 10 },
    { id: "p2", team: "red", score: 30 },
    { id: "p3", team: "blue", score: 20 },
  ]) {
    const res = await h.api.data("POST", `/documents/${col}/${row.id}`, { data: row });
    check(res.status === 201, `seed player ${row.id}`);
  }

  const created = await h.api.data("POST", "/indexes", { collectionPath: col, fields });
  check(created.status === 201 || created.status === 409, "index creation is 201 or duplicate 409");
  const alreadyExists = created.status === 409;
  h.log({ createStatus: created.status, outcome: alreadyExists ? "already exists" : "created" });

  const listed = await h.api.data("GET", "/indexes");
  check(listed.ok, "index listing succeeded");
  const found = listed.body.indexes.find((index) => index.collectionPath === col);
  check(Boolean(found) || alreadyExists, "created index appears in the listing");
  h.log({ listed: listed.body.indexes.length > 0, foundInListing: Boolean(found) });

  const rows = await h.api.data("POST", "/query", {
    collectionPath: col,
    where: [{ field: "team", op: "==", value: "red" }],
    orderBy: [{ field: "score", dir: "asc" }],
    limit: 50,
    select: null,
    startAt: null,
    startAfter: null,
  });
  const ids = rows.body.documents.map((d) => d.documentId);
  check(rows.ok && ids.length === 2, "indexed query returned both red-team rows");
  h.log({
    query: "team == red ORDER BY score ASC",
    ids,
    indexUsed: rows.body.meta?.indexUsed,
  });

  if (found) {
    const removed = await h.api.data("DELETE", `/indexes/${found.id}`);
    check(removed.ok, "index deletion succeeded");
    h.log({ deleted: true });
  }
} finally {
  await h.cleanup();
}
